**作成日:** 2026-08-01 / 読む深さ: 📗 使い捨て（実装の設計判断メモ。CEO が読む必要があるのは §1 と §6 だけ）

## 1. CEO が使う分（これだけ読めばよい）

**既定で何が起きるか。** ブラウザが裏にあるとき、セッションが「承認待ち」か「質問」になったら macOS の通知が出る。通知のタイトルはそのセッションの AI サマリー（なければディレクトリ名）、本文は状態語そのもの。クリックするとウィンドウが前に出て、そのセルにカーソルが入る。「完了・未読」は**既定では通知しない**（後述）。

**許可の求め方。** 初回のクリックかキー入力の後に一度だけ聞く。起動直後にポップアップは出さない。一度「許可しない」を押すと config では戻せない — ブラウザのサイト設定から再許可する必要がある。

**うるさかったら。** `~/.mulmoterminal/config.json` に:

```json
{ "notifyKinds": ["approval"] }
```

承認待ちだけになる。`[]` で全部止まる（チャイムとタブの件数は残る）。逆に完了も通知させたいなら `["approval", "question", "unread"]`。

**タブに件数が出る。** favicon の右上に赤い丸で「要対応（承認待ち + 質問）の件数」、タブのタイトルにも `(3) mulmoterminal`。30 ペイン運用でタブが細くなってもどちらかは読める。

## 2. なぜ 3 つの抑制がハードコードなのか

claudecode-notify が実運用で持っていた作法をそのまま移植した。この 3 つは設定にしていない — 外せると「全部切る」に倒れて機能ごと死ぬため。

| 抑制 | 理由 |
|---|---|
| 同一セッション × 同一種別で 5 分クールダウン | 1 つの長いタスクが許可を繰り返し求める。1 回ずつ通知したら 1 タスクで数十発になる |
| ページが**可視 かつ フォーカスあり**なら出さない | 見ている画面の上にその画面の話をするポップアップが出るのは純粋なノイズ。枠色とチャイムで足りている |
| 1 セッションにつき通知は 1 枚（`tag` で置換） | 30 エージェントが 30 枚のポップアップになってはいけない |

**可視の判定を「可視 AND フォーカス」の 2 条件にした理由:** 可視だがフォーカスのないタブ = 別ウィンドウを見ている状態で、これはまさに通知が要る場面。`visibilityState` だけで判定すると、隣のウィンドウで作業中に通知が消える。

**クールダウンを「実際に出したときだけ」刻む理由（実装上の要点）:** 可視で抑制されたメッセージがクールダウンを開始してしまうと、その 1 秒後に席を立った CEO は 5 分間何も聞けない。`notifyDecision` は状態マップを毎回更新し、クールダウンは通知を出した瞬間にだけ刻む。spec で固定してある。

## 3. なぜ `pushKinds` と別設定なのか（R14 の指示どおり）

| | `pushKinds` | `notifyKinds` |
|---|---|---|
| 宛先 | 電話（Web Push・`pushEnabled` + RemoteHost 接続が要る） | この機械のブラウザ |
| 語彙 | `finished` / `waiting`（hook 名由来） | `approval` / `question` / `unread`（状態語 6 値の部分集合） |
| 決める側 | サーバー | クライアント |

同じ「通知」でも、欲しい瞬間が違う。電話は「終わったこと」を知りたい（席にいないので後追いでよい）が、机の前では終了通知は最も頻度が高く最もノイズになる。したがって既定値も違う: `pushKinds` は両方 ON、`notifyKinds` は `unread` を外してある。

`NotifyKind` は `PaneState` からの `Extract` にした。状態語を消したり改名したらコンパイルが落ちる。通知本文は `paneStateWord()` をそのまま使うので、セルの表示と通知の文言が食い違うことは原理的に起きない。

## 4. 音の作り分け（要求 3）

- **緊急（承認待ち・質問）** = 既存の 2 音（G5 → C6）。**一切変えていない**
- **控えめ（完了・未読）** = D5 の 1 音、ゲインは既存の 0.25 に対し 0.1

判定は `attentionToneFor()` が `paneStateOf()` 経由で行う。フラグを直接読まないので、状態語・通知種別・チャイムの 3 つが同じ 1 つの規則から出る。

**dir 別 sound 設定の互換:** 変えていない。ディレクトリの `.mulmoterminal.json` の音、およびグローバルの `soundFile` は**全種別で今までどおりそのまま鳴る**。種別で鳴り分けるのは組み込みチャイムだけ。理由: ファイルを指定するのは「この音にしろ」というユーザーの明示的な選択で、状態ごとに勝手に差し替えたらその選択を上書きすることになる。

## 5. 通知クリックの着地

通知はセッション id しか持たない。どのセルがそれを持っているか・そのセルが何ページ目かを知っているのはグリッドだけなので、`useAgentColumn` と同じ「登録 + キュー」方式にした（`useRevealSession.ts`）。

`useAgentColumn` と 1 点だけ違う: **キューは最新の 1 件だけ持つ**。列の依頼はホストがエージェントに「開いた」と返事済みの仕事なので落とすと列が消えるが、reveal は「数回前の通知のときに行きたかった場所」で、溜めて再生したら呼んだ全セッションを順に巡って最後から 2 番目に着地する。

着地の手順: `window.focus()` → 該当セルのページへ切替（ズーム中はページを動かさない — CEO が離れていないズームを勝手に畳むことになる）→ `conn.focus('cell-<uid>')` でそのターミナルにカーソル。`next-attention` キーの着地と同じ。

## 6. 実装した範囲と、実機で確認していないこと

**入っているもの:** ブラウザ通知（種別・クールダウン・可視抑制・kinds フィルタ・クリック着地）/ チャイムの作り分け / favicon バッジ + タイトル件数 / `notifyKinds` 設定（サーバー型・サニタイズ・スキル記述）/ Vitest 42 件追加（該当 4 ファイル計 54 件・全 4890 件 green）。

**⚠️ 実機で未確認（コードとテストは通っているが、CEO の環境での挙動は未検証）:**

1. **macOS の通知センターでの実際の見た目**（jsdom には Notification API が無いため、モックでしか検証していない）
2. **`http://localhost:34567` が secure context として通ること** — localhost は仕様上 secure なので通るはずだが実測していない。**LAN の IP 直打ち（`http://192.168.x.x:34567`）では Notification API 自体が存在しない**。その場合も落ちずにチャイムとバッジだけになることは spec で固定してある
3. **favicon バッジの 16px での可読性** — jsdom に canvas が無く、描画結果を見ていない。9 超は `9+` に丸めてある
4. **常駐 launchd + ブラウザ再起動をまたいだ許可の永続性**

いずれも「ブラウザを裏にして承認待ちを 1 回起こす」で 5 分あれば確認できる。Gate 1 のドッグフーディングで最初に見るべき項目。

**やっていないこと（R14 のうち意図的に落とした分）:** メニューバー相当の常時可視性。ブラウザからは原理的に届かない領域で、PWA インストール + Badging API が候補だが、CEO は常駐サーバーを常時タブで開いている運用なので、タブの favicon 件数が事実上その役を果たす。R15（外出時経路）とあわせて Gate 1 の結果を見てから判断する。
